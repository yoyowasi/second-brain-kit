# 세컨드 브레인 운영 규칙 (AI 에이전트 공통)

이 파일이 Claude Code·Codex·Gemini CLI 같은 AI 에이전트가 함께 따르는 단일 기준이다. `CLAUDE.md`, `GEMINI.md`는 이 파일을 가리키기만 하고, Codex는 이 파일을 직접 읽는다. 규칙을 바꿀 때는 이 파일만 고친다.

## 판단 기준

- 판단이 애매할 때는 [[나의 판단 방식]](`30_Areas/나의 판단 방식.md`)을 기본값으로 따른다.
- 우선순위: 사용자의 그때그때 지시 > 이 파일 > second-brain 스킬의 `local.md`(있으면) > [[나의 판단 방식]] > 스킬 기본값.
- 그 노트에 해당 원칙이 없거나 원칙끼리 부딪치면 짧게 묻는다. 지우기·덮어쓰기처럼 되돌리기 어려운 일은 언제나 먼저 묻는다.

## 작업 범위와 보안

- 작업 범위는 이 볼트 폴더(이 파일이 있는 폴더)다. 노트 생성·수정은 볼트 안에서만 하고, 볼트 밖 파일은 쓰지 않는다.
- 볼트 밖 폴더(외부 원본 폴더: 업무 일지, 다른 메모 폴더 등)는 아래 "열어도 되는 곳"(또는 second-brain 스킬 `local.md`)에 적혀 있고 사용자가 요청할 때만 **읽는다**. 쓰지는 않는다.
- 다음은 열지도, 인용하지도, 요약하지도 않는다: `.obsidian/`, `.trash/`, 이름에 `토큰`·`비번`·`비밀번호`·`password`·`passwd`·`token`·`secret`·`credential`이 들어갔거나 `.env`·`.pem`·`.key`로 끝나는 파일과 그런 이름의 폴더, 아래 "열지 않을 곳"에 적은 폴더·파일.
- 노트에 비밀번호·토큰·API 키·개인 식별번호(주민등록번호, 카드번호 등)를 적지 않는다. 사용자가 붙여넣었으면 `[비밀정보 제거됨]`으로 바꾸고 알린다.
- 노트는 지우지 않는다. 필요 없어지면 `90_Archive/`로 옮긴다.
- 파일 이름을 바꾸면 볼트 안의 `[[링크]]`를 함께 고친다. 볼트 밖 파일의 링크는 고치지 말고 보고만 한다.
- 볼트를 git(예: Obsidian Git 플러그인)으로 백업하면 노트 내용이 원격 저장소로 나간다. 저장소는 반드시 private으로 둔다.

### 사용자가 채우는 자리

### 분류 질문 (위에서부터 차례로)

1. 끝나는 날이나 완료 조건이 있나? → `20_Projects/`
2. 계속 관리하는 책임(업무, 건강 등)에 관한 것인가? → 기준·원칙 한두 줄이면 그 영역 노트(`30_Areas/`)의 "지키고 싶은 기준"에 덧붙인다(무인 루틴에서는 후보로만 적는다). 그보다 길면 성격에 맞게 참고 자료(4번)나 영구 노트(5번)로 만들고 `area`에 그 영역을 링크한다. 새 영역 노트는 사용자가 원할 때만 만든다.
3. 문제를 해결한 기록인가? → `40_Resources/해결 기록/`
4. 나중에 찾아볼 자료인가? → `40_Resources/참고 자료/`
5. 내 생각을 한 문장 주장으로 쓸 수 있나? → `50_Notes/`
6. 그날 할 일이나 그날의 기록인가? → 오늘 일일 노트
7. 그래도 모르겠으면 인박스에 그대로 두고 이유를 보고한다.

## 자동 기록과 승인

- **저절로 쌓이는 것은 셋뿐이다**(Claude Code hook을 설치했을 때): 세션 일지(`10_Daily/Journal/`), dream 규칙 제안(`00_Inbox/`의 `type: dream`), 색인(`99_System/색인.md`). 에이전트·루틴은 이 파일들을 손으로 고치지 않는다(dream 제안은 아래 "인박스 정리" 4번).
- **사용자가 요청하거나 승인할 때만 쓰는 것**: 영구 노트, 종합·비교·분석·웹 조사 노트("브레인에 남기기"), 저장소 노트, 규칙 반영(에이전트 지침 파일·이 파일, dream 제안 반영). 잘못 알아들은 내용이 저절로 굳지 않게 하려는 것이다.
- 작업 중 새로 확인한 사실(해결 기록·참고 자료)을 묻지 않고 남길지는 second-brain 스킬 `local.md`의 기록 정책을 따른다. 정책이 없으면 남길지 먼저 묻는다.
- 볼트 git 커밋·push는 사용자가 요청할 때만 한다(Obsidian Git 같은 백업 도구를 쓰면 그 도구가 한다).

## 노트 형식

- 언어는 사용자의 언어(기본 한국어)로 쓴다. 파일 이름은 내용을 알 수 있는 짧은 제목으로 짓는다(일일·주간 노트 제외). `/ \ : * ? " < > |`는 쓰지 않는다.
- 본문 첫 제목(`# `)은 파일 이름과 같게 쓴다. 주간 노트(`YYYY-Www 주간 리뷰`)와 `type: system` 노트는 예외이고, 인박스 노트는 제목을 생략해도 된다.
- 맨 위에 프로퍼티(frontmatter)를 둔다.

```yaml
---
type: inbox | daily | weekly | project | area | resource | fix | note | system | repo | check   # journal·dream은 hook 전용, check는 점검 결과
status: active          # project만: active | done | paused
due: 2026-12-31         # project만, 마감이 있을 때
start: 2026-10-12       # weekly만: 그 주 월요일
end: 2026-10-18         # weekly만: 그 주 일요일
area: "[[업무]]"         # 관련 영역이 있으면
tags: []
created: 2026-10-15T09:00
---
```

- `created`는 만든 시각을 `YYYY-MM-DDTHH:mm` 형식(로컬 시간)으로 적는다.
- `updated`는 에이전트가 쓰지 않는다. 수정 시각을 자동으로 적는 플러그인을 쓰면 그 플러그인이 관리한다. 템플릿이나 다른 노트에 있어도 새 노트로 복사하지 않는다.
- 새 노트는 `99_System/Templates/`의 해당 템플릿 구조를 따른다. 에이전트가 파일을 직접 만들 때는 템플릿의 Templater 구문(퍼센트 기호와 꺾쇠 괄호로 감싼 부분)을 실제 값으로 바꿔 쓴다. 템플릿 폴더 밖 노트에는 Templater 구문을 남기지 않는다. second-brain 스킬이 있으면 `sb.py new`·`sb.py render`가 이 치환을 맡는다.
- Templater가 새 파일이 생길 때 자동 실행되도록 설정되어 있으면, Obsidian이 켜진 동안 구문이 든 파일을 새로 넣는 순간 구문이 실행되어 `undefined` 등으로 망가진다. 템플릿 파일을 새로 만들어야 하면 사용자에게 Obsidian을 닫거나 그 설정을 잠시 꺼 달라고 먼저 알린다.
- 관련 노트는 `[[노트 이름]]`으로 연결한다. 새 노트는 최소 하나의 기존 노트(영역, 프로젝트, 관련 노트)에 연결한다. 고아 노트를 만들지 않는다. 인박스·일일·주간 노트는 예외다.
- **찾고 나서 쓰기**: 새 노트를 만들기 전에 `99_System/색인.md`(있으면) → 볼트 안 `rg -il <키워드>` 순으로 같은 주제를 찾고, 있으면 그 노트를 고친다. 자료 하나가 여러 노트(프로젝트·참고 자료·영역)를 건드리면 각각에 반영하고 서로 링크한다.
- **출처**: 외부 자료는 링크와 원본 위치를 출처 절에 적는다(참고 자료는 `## 원본`, 해결 기록은 템플릿의 출처 절, 그 밖은 노트 끝 `## 출처`). 웹 조사 노트는 맨 위에 `조사일: YYYY-MM-DD`를 두고, 공식 문서로 확인하지 못한 내용은 그렇다고 밝힌다.
- **충돌**: 새 자료가 기존 내용과 어긋나는데 어느 쪽이 맞는지 모르면 지우지 말고 둘 다 출처와 함께 적은 뒤 `> 충돌: 무엇이 어긋나는지`를 단다. 정리되면 이 줄을 지운다(`sb.py lint`가 남은 충돌을 알려 준다).
- **보관**: 낡은 노트는 지우지 않고 맨 위(제목 아래)에 `> 보관: 이유`를 단 뒤 `90_Archive/`로 옮긴다.

## 태그

- 적게 시작한다. 폴더와 `type`으로 이미 구분되는 것은 태그로 반복하지 않는다.
- 태그 어휘는 영역마다 그 영역 노트의 "태그 어휘" 절에 목록으로 둔다(예: [[업무]]). 다른 영역에 태그가 필요해지면 그 영역 노트에 같은 절을 만든다. `미결`은 모든 영역에서 같이 쓴다. second-brain 스킬의 `local.md`에도 태그 어휘를 적었다면 같은 목록으로 맞춘다.
- 어느 영역 노트의 목록에도 없는 태그는 새로 만들지 말고 가장 가까운 기존 태그를 쓴다. 꼭 필요하면 보고에 "새 태그 제안"으로 남기고, 사용자가 정하면 목록에 추가한다.
- frontmatter에는 `#` 없이 쓴다: `tags: [자동화, 미결]`. 띄어쓰기 대신 `-`를 쓴다.
- `미결`은 아직 결론이 나지 않은 노트에 붙이고, 결론이 나면 뗀다.

## 할 일

- 할 일의 원본은 한 곳에만 둔다. 며칠 이어지는 일은 프로젝트 노트의 `## 할 일`에, 그날 끝낼 일만 일일 노트의 `## 할 일`에 적는다. 같은 할 일을 복사하지 않는다.
- 형식: `- [ ] 내용`. 마감이 있으면 `- [ ] 내용 📅 YYYY-MM-DD`처럼 붙인다. 끝나면 `- [x]`로 바꾼다.
- 할 일을 다른 노트로 옮길 때는 원래 줄을 `- [x] → [[프로젝트 이름]]로 이동`으로 바꾼다.
- 미완료 항목은 Home의 "열린 할 일"과 `sb.py tasks`에 계속 보이므로 날마다 옮겨 적지 않는다.

## 반복 작업 (사용자가 이렇게 부르면 실행)

### 메모 ("메모해 둬")
1. `00_Inbox/`에 `Inbox` 템플릿으로 새 노트를 만든다. 제목은 내용을 알 수 있는 짧은 말로 짓는다.
2. 사용자가 한 말을 그대로 적는다. 분류는 하지 않는다(나중에 인박스 정리에서 한다).

### 할 일 추가 ("할 일 추가해줘")
1. 그날 끝낼 일이면 오늘 일일 노트(없으면 "오늘 노트" 절차로 만든다)의 `## 할 일`에 넣는다.
2. 며칠 걸리거나 특정 프로젝트의 일이면 그 프로젝트 노트의 `## 할 일`에 넣는다. 어느 프로젝트인지 애매하면 오늘 노트에 넣고 그렇게 했다고 알린다.
3. 마감을 말했으면 `📅 YYYY-MM-DD`를 붙인다. "금요일까지"처럼 말했으면 실제 날짜로 바꾼다.

### 인박스 정리
1. `00_Inbox/`의 노트를 하나씩 읽는다.
2. 위 "분류 질문"으로 분류해 옮기고, `type`·`area`·`tags`를 채우고, 관련 노트에 링크한다. 한 메모에 여러 내용이 섞여 있으면 나눈다. 나눠서 내용이 모두 다른 노트로 옮겨졌으면 원본 인박스 노트는 `90_Archive/`로 옮긴다.
3. 같은 주제의 기존 노트가 있으면 새로 만들지 말고 기존 노트에 합친다(영역 노트에 기준을 덧붙인 경우도 같다). 합친 원본 인박스 노트는 `90_Archive/`로 옮긴다.
4. 분류가 확실하지 않은 것은 인박스에 두고 이유를 보고한다. `type: dream` 파일(dream 규칙 제안)과 `type: check` 파일(점검 결과)은 사용자 결정 대상이다. 사용자와 대화 중일 때만 Claude Code `/inbox` 절차로 처리하고, 무인 루틴·다른 에이전트는 손대지 않고 "인박스에 남김: dream 제안·점검 결과(사용자 결정 필요)"로 보고한다(예외: 사용자가 부른 "점검" 3번의 이어받기).
5. 무엇을 어디로 옮겼는지 표(원래 이름 → 위치)로 보고한다.

### 오늘 노트
1. `10_Daily/YYYY-MM-DD.md`가 없으면 `Daily` 템플릿으로 만든다. 이미 있으면 지우거나 덮어쓰지 않는다. `sb.py new daily`가 다른 폴더에 있는 같은 이름 파일(예: 링크를 눌러 볼트 최상위에 생긴 빈 노트) 때문에 거부되면, 그 경로를 보고하고 옮길지 사용자에게 묻는다.
2. 지난 일일 노트의 미완료 항목은 복사하지 않는다. 이틀 넘게 남은 항목은 사용자에게 알리고, 사용자가 정하면 관련 프로젝트 노트로 옮긴다(위 "할 일" 규칙).
3. 사용자가 외부 원본(예: 업무 일지 폴더의 같은 날짜 파일)을 붙여 달라고 하고 그 폴더가 "열어도 되는 곳"에 있으면, 그 파일을 읽어 3~8줄로 요약하고 원본 링크와 함께 `## 기록`에 붙인다. 원본에 없는 내용은 지어내지 않는다. `~/.second-brain/config.json`의 `today_sources`에 경로 패턴을 넣어 두면 `sb.py today`가 그 파일 위치를 같이 보여 준다.

### 주간 리뷰
1. 대상 주(ISO 주차, 월~일)를 정한다. 사용자가 말하지 않으면 이번 주.
2. 그 주 `start`~`end`에 해당하는 일일 노트, 그 기간에 생긴 노트, 진행 중 프로젝트를 읽는다.
3. `10_Daily/Weekly/YYYY-Www.md`(예: `2026-W42.md`)를 `Weekly` 템플릿으로 만들어 채운다. 이미 있으면 비어 있는 절만 채운다. 한 일·배운 것·막힌 것·다음 주 우선순위 3개를 쓴다.
4. 2주 넘게 손대지 않은 `status: active` 프로젝트를 목록으로 알려 준다(`sb.py stale`). 상태는 사용자가 정한다.
5. 주간 노트는 에이전트나 `sb.py new weekly`로 만든다. `Weekly` 템플릿은 파일 이름(`2026-W42` 형식)으로 `start`·`end`를 계산하므로, 사용자가 Obsidian에서 직접 만들 때는 파일 이름을 먼저 그 형식으로 지은 뒤 템플릿을 적용하라고 안내한다.

### 노트 정제 ("`[[노트]]`에서 노트 정제해줘")
1. 사용자가 지정한 노트(참고 자료, 일일 노트, 해결 기록 등)에서 다시 쓸 만한 생각을 찾는다.
2. 생각 하나당 `50_Notes/`에 영구 노트 하나를 `Note` 템플릿으로 만든다. 제목은 한 문장 주장, 본문은 내 말로 3~10줄, 출처 링크는 필수다.
3. 원본에 없는 내용을 더하지 않는다. 추측은 `> 추측:`으로 표시한다.

### 해결 기록 ("이거 해결 기록 남겨줘")
1. 사용자가 해결한 문제(오류, 장애, 설정, 데이터 문제 등)를 `40_Resources/해결 기록/`에 `Fix` 템플릿으로 남긴다. 제목은 증상 한 줄.
2. 현상 → 원인 → 변경 → 검증 → 출처 순서로 쓴다. 원인은 줄마다 `확인:`과 `추정:`으로 나누고, 검증에는 실제로 확인한 범위만 적고 하지 않은 범위는 `미확인:`으로 적는다.
3. 관련 프로젝트나 영역에 링크한다(`area` 기본값은 [[업무]], 다른 영역이면 바꾼다). 증상과 원인 기제가 같은 기존 기록이 있으면 그 노트에 사례를 추가한다. 증상이 비슷해도 원인이 다르면 새 노트를 만들고 서로 링크한다.

### 참고 자료 정리 ("참고 자료로 정리해줘")
1. 사용자가 준 글·링크·자료를 `40_Resources/참고 자료/`에 `Resource` 템플릿으로 정리한다. 제목은 주제를 알 수 있는 짧은 말.
2. 제목 아래에 한 줄 설명, `## 요약`에 내 말로 3~7줄, `## 원본`에 링크나 출처를 적는다. 원문이나 큰 표를 길게 옮겨 적지 않는다.
3. 관련 영역이나 프로젝트에 링크한다. 같은 주제의 참고 자료가 있으면 그 노트에 합친다.

### 질문에 답하기 ("볼트 기준으로 ○○ 알려줘", "전에 이거 해결한 적 있나")
- 볼트 노트를 근거로 답하고, 근거 노트를 `[[링크]]`로 밝힌다.
- 해결 사례를 물으면 `40_Resources/해결 기록/`부터 찾는다.
- 볼트에 없는 내용은 "볼트에 없음"이라고 먼저 말한 뒤 일반 지식으로 보충하고, 둘을 구분해 쓴다.
- 찾는 순서: `99_System/색인.md`(있으면)에서 폴더·노트를 고르고 그 노트를 연다. 없거나 날짜·세부가 필요하면 볼트 안에서 `rg -il <키워드>`. 지난 작업 흐름은 `10_Daily/Journal/`(세션 일지)도 본다.

### 기억하기 ("기억해", "브레인에 넣어")
1. 지식·사실·결정이면 "찾고 나서 쓰기"대로 맞는 노트(해결 기록·참고 자료·프로젝트·영구 노트)를 고치거나 만든다. 분류가 애매하면 인박스에 적는다.
2. AI의 작업 방식에 대한 교정·규칙이면 볼트가 아니라 그 에이전트의 메모리·지침 파일에 둔다(모든 프로젝트에 통하는 규칙이면 전역에 둘지 먼저 묻는다).
3. 볼트에 썼으면 `99_System/브레인 로그.md`에 `ingest`로 남긴다.

### 브레인에 남기기 (query)
1. 답이 다시 쓸 만한 종합·비교·분석이나 웹 조사 결과면 답 끝에 "브레인에 남길까요?"를 한 줄로 묻는다. 단순 사실 확인, 코드 작업 보고, 이미 볼트에 있는 내용이면 묻지 않는다.
2. 남기라고 하면 "찾고 나서 쓰기"대로 기존 노트를 고치거나 맞는 종류로 새 노트를 만들고(웹 조사는 `조사일:`과 출처), 관련 노트에 링크한다.
3. `99_System/브레인 로그.md`에 `query`로 남긴다.

### 저장소 노트
- Claude Code `/init-project [경로]`가 코드 저장소를 읽기만 하고 `40_Resources/저장소/<이름>.md`를 만들거나 고친다. 틀: `> 한 줄 요약`, `## 개요`, `## 위치`(경로·원격·배포), `## 스택`, `## 기능`(10줄 이내), `## 구조와 흐름`(3~7줄, 무엇이 무엇을 부르는지와 이유), `## 현재 상태`(날짜), `## 주요 결정`(`- (날짜) 결정 — 이유`), `## 다음 할 일`, `## 관련`.
- 함수·파일 단위 설명과 API 목록은 넣지 않는다(금방 낡는다). 다시 만들 때 `## 주요 결정`·`## 다음 할 일`은 지우지 않고 덧붙인다. 그 저장소의 할 일이 active 프로젝트에 이미 있으면 복사하지 않고 링크만 둔다.

### 점검 ("세컨드 브레인 점검", "브레인 점검", "볼트 점검")
1. `sb.py`(second-brain 스킬의 `scripts/sb.py`)로 `index`(색인 새로 만들기)와 `lint`(형식, 깨진 링크, 고아 노트, 비밀정보, 남은 `> 충돌:`)를 돌린다. 볼트 안 링크·형식 문제는 고친다.
2. 내용 점검: 낡은 주장(오래된 버전·상태 문장, 끝났는데 `active`인 프로젝트, 오래 남은 `미결`), 할 일 원본 중복(`tasks`), 2주 넘게 방치된 active 프로젝트(`stale`), 같은 주제가 여러 노트로 갈라진 곳. 내용 판단이 필요한 것은 고치지 않는다(상태·사실은 사용자가 정한다).
3. **결정이 필요한 항목은 점검 결과로 남긴다(묻지 않고 만든다).** `sb.py new check "YYYY-MM-DD 점검 결과"`로 `00_Inbox/`에 만든다. 같은 이름이 볼트 어디에든 있으면(같은 날 두 번째 점검, 보관된 파일) `YYYY-MM-DD 점검 결과 2`(3, …)로 만든다.
   - 틀(`sb.py`가 없으면 직접): frontmatter `type: check`·`tags: []`·`created`, `# 제목`, `> 🤖 …/inbox에서 하나씩 정한다…` 안내, `## 결정 대기`(묶음은 `### A. 이름`), `## 웹으로 채울 빈칸`(체크박스 없이 `- `), `## 처리 결과`.
   - 항목 형식: `- [ ] [ID] [[대상 노트]] — 문제 한 줄 · 근거(노트:줄, 일지·로그) · 선택지` (ID는 묶음 글자+번호, 예 A1). 근거가 '확인 필요'인 것은 그렇게 적고 사실처럼 쓰지 않는다.
   - 같은 문제는 한 항목으로 묶는다. 이번 점검에서 이미 고친 것은 넣지 않고 `## 처리 결과`에 `- [x] 고침: …`으로 적는다. 머리말에 `결정 대기 N항목(지적 M건을 묶음)`을 적고, 보고·로그에도 같은 숫자를 쓴다.
   - **이어받기**(이 경우에만 점검이 앞선 점검 결과 파일을 고친다): 인박스에 앞선 점검 결과(`type: check`)가 있으면 모두 읽는다. 아직 유효한 미처리 항목은 새 파일의 맞는 묶음에 새 ID로 옮기고 `[A1] (← 10-19 A3)`처럼 원래 ID를 붙인다(`→ 보류: …` 꼬리도 그대로 옮긴다). 앞선 파일의 그 줄은 `- [x] [A3] … → [[새 파일]] A1로 이동`으로 바꾼다. 대상 줄·링크·태그가 이미 바뀌어 문제가 객관적으로 사라진 항목만 `- [x] … → 해결됨(노트:줄 근거)`으로 바꾸고, 판단이 필요하면 미처리로 옮긴다. 아직 안 채운 `## 웹으로 채울 빈칸` 줄도 옮긴다. 앞선 파일 끝에 `→ [[새 파일]]로 이어짐`을 단 뒤 `90_Archive/`로 옮긴다.
   - 처리는 사용자가 Claude Code `/inbox`에서 한다. 정한 항목은 `- [x] … → 결정: 내용 (YYYY-MM-DD)`. `## 결정 대기`에 `- [ ]`가 없으면 `90_Archive/`로 옮긴다.
4. 보고 끝에 웹 검색으로 채울 빈칸과 다음에 파고들 질문을 3개 이내로 제안한다(점검 결과의 `## 웹으로 채울 빈칸`에도 적는다).
5. `99_System/브레인 로그.md`에 `lint`로 남긴다(`--pages`에 고친 노트와 점검 결과 노트). `lint`는 실제 점검에만 쓴다(점검 결과 처리는 `ingest`).

### 작업 기록 형식 (`99_System/브레인 로그.md`)
- 추가만 한다(`sb.py log`). 머리줄은 `## [YYYY-MM-DD] ingest|query|lint | 제목`, 다음 줄에 `- 원본: ...`, `- 고친 노트: [[...]]`. 종류는 셋뿐이다(인박스·자료 반영 = ingest, 남기기 = query, 점검 = lint). 그냥 찾아서 답만 한 질문은 적지 않는다.

### 무인 루틴
- `99_System/Routines/`의 파일은 예약 실행용 프롬프트다. 루틴으로 실행될 때는 질문하지 않고, 루틴이 지정한 파일 외에는 고치지 않는다.
- 위 절차 중 지정한 파일 밖을 고쳐야 하는 일(메모 나누기, 기존 노트에 합치기, 영역 노트에 덧붙이기, 오늘 노트로 옮기기 등)은 하지 않고, 원래 자리에 둔 채 결과에 "후보"로 적는다.
