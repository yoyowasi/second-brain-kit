# 기록하기 (해결 기록 · 참고 자료 · 영구 노트)

## 무엇을 기록하나

- **기록한다**: 다시 겪을 만한 문제의 원인·변경·검증, 환경 특성(개발·운영 데이터 차이, 버전별 동작), 업무 규칙, 대응표·설정값, 내 말로 정리한 생각.
- **기록하지 않는다**: 한 번 쓰고 버릴 로그, 확인 안 된 추측만 있는 것, 비밀정보, 실제 고객·개인 데이터 행.

## 1. 중복 확인 (쓰기 전에 반드시)

[search.md](search.md) 방식으로 같은 주제를 찾는다. 오늘·어제 일일 노트의 `🤖 해결 기록 후보:` 줄도 본다.

| 상황 | 할 일 |
|---|---|
| 증상과 원인 기제가 같다 | 기존 노트에 사례를 덧붙인다 |
| 같은 화면·모듈이지만 증상이 다르다 | 새 노트를 만들고 서로 링크한다 |
| 증상만 비슷하고 원인이 다르다(예: 둘 다 "0건") | 새 노트를 만들고 서로 링크한다. 기존 노트가 "일반화하지 말라"고 적었으면 특히 |
| 애매하다 | 후보 2~3개를 보여 주고 묻는다 |
| 대상(화면·파일)이 정해지지 않았거나 찾은 증거가 사용자 말과 어긋난다 | **쓰기 전에** 후보와 증거(예: git 이력, 파일 수정 시각)를 보여 주고 한 번 묻는다 |

**사례 덧붙이기 형식**
- 기존 본문은 고치지 않는다. 기존 본문이 사례 1이다(머리글을 새로 달지 않는다).
- 맨 끝에 `## 사례 N — YYYY-MM-DD · 맥락(저장소·화면)`을 두고 그 아래 `### 현상`/`### 원인`/`### 변경`/`### 검증`/`### 출처`를 같은 규칙으로 쓴다.
- tags는 합집합만 갱신한다. 사례 하나라도 미해결이면 `미결`을 더하고, 모두 해결되면 뺀다.
- 오늘 일일 노트 `## 오늘 배운 것`에 `- [[제목]] — 사례 N`을 단다.
- 같은 화면의 다른 증상 노트와는 양쪽에 링크한다.

## 2. 해결 기록 (Fix)

- 만들기: `sb new fix "<증상 한 줄>"`. 제목은 원인 없이 보이는 증상만, 현재형 평서문: "[맥락]에서 [대상]이 [증상]다". 금지 문자 `/ \ : * ? " < > |`.
- **현상**: 어디서(저장소·화면·모듈), 어떤 조건에서, 무엇이 보였나. 관찰 수치.
- **원인**: 줄마다 `확인:`(어떻게 확인했는지 — 실행, 로그, 코드 읽기, git 이력) 또는 `추정:`. 에이전트 메모리·다른 노트에서 가져온 사실은 `확인(메모리 기준):`처럼 출처를 붙인다. 사용자 말과 어긋나는 증거를 찾았으면 그것도 `확인:` 줄로 남긴다. 일반화하면 안 되는 범위도 적는다. "결함이 아니다" 같은 평가 문장은 쓰지 않는다.
- **변경**: 실제로 바꾼 파일만(저장소 기준 상대 경로). 바꾼 파일을 모르면 `git log`/`git diff`로 읽기 전용 확인하고, 그래도 모르면 `미확인`으로 둔다. 바뀌지 않은 파일을 변경·출처에 올리지 않는다. 설정·데이터 변경과 백업 위치, 적용하지 않은 우회, 외부 팀에 요청한 것(요청 여부를 모르면 "요청 여부 미확인")을 구분한다. 사용자가 하지 않은 일을 가정해 적지 않는다.
- **검증**: 범위 라벨로 실제로 한 것만 적는다 — `코드(정적: 타입 검사·빌드·테스트)`, `API`, `DB(환경, 실행한 쿼리·프로시저)`, `브라우저(환경, 날짜, 조건)`, `운영`. 하지 않은 범위는 `미확인:`으로 나열한다.
  - 사용자가 말로 알려 준 검증은 `(사용자 보고, YYYY-MM-DD)`로 적는다. 사용자가 말하지 않은 환경·DB·프로시저 이름·저장소·포트는 채우지 않는다(추론은 `추정:`).
  - 세션에서 직접 확인하지 않고 다른 기록을 옮겼다면 그렇게 밝힌다.
- **날짜**: 노트·출처의 날짜는 실제로 쓰는 시점에 `sb today`로 다시 얻는다(계획을 세운 날과 다를 수 있다).
- **출처**: `[[YYYY-MM-DD]]`(해결한 날 일일 노트), 관련 프로젝트, 커밋, 원본 문서 링크. 절대 경로는 쓰지 않는다.

## 3. 참고 자료 (Resource)

- 만들기: `sb new resource "<짧은 주제>"`. 구조: 한 줄 설명(+관련 프로젝트 링크) → `## 요약`(대표 예시 몇 개) → `## 원본`(원본 링크·위치).
- 큰 표 전체를 복사하지 않는다. 요약과 원본 위치를 남긴다.

## 4. 영구 노트 (Note)

- 만들기: `sb new note "<한 문장 주장>"`. 본문은 내 말로 3~10줄, `## 근거 · 출처` 필수, 추측은 `> 추측:`.

## 5. 태그·연결

- 태그는 `local.md`의 어휘가 있으면 그것만, 없으면 `sb tags`로 쓰던 것을 고른다. 새 태그가 필요하면 보고에 적는다(대시보드가 태그 목록으로 묶는 볼트가 많다). 미해결이면 `미결`.
- 최소 하나의 기존 노트(관련 프로젝트, 영역 노트, 관련 해결 기록)에 링크한다. 같은 기제의 다른 해결 기록·참고 자료가 있으면 서로 링크한다.
- 역링크: 오늘 일일 노트 `## 오늘 배운 것`에 `- [[새 노트]]`를 더한다. 진행 중 프로젝트의 일이면 그 프로젝트 `## 진행 기록`에 `- YYYY-MM-DD [[새 노트]]`.
- 에이전트 메모리에도 같은 사실을 남기면 그 메모리에 볼트 노트의 **절대 경로**를 적는다(다른 프로젝트 세션에서도 열 수 있게).
- `미결`의 뜻: 원인만 확인했거나 수정이 외부(다른 팀·라이브러리 업데이트)에 달려 있으면 미해결이다. `local.md`가 달리 정하면 그것을 따른다.

## 6. 비밀정보 거르기 (쓰기 전에)

초안에서 다음을 찾아 `[비밀정보 제거됨]`으로 바꾸고 사용자에게 알린다.

- 접속 문자열: `Server=`, `Data Source=`, `jdbc:`, `User ID=`, `Password=`, `pwd=`, `mongodb://user:pass@`
- 인증: `Authorization:`, `Bearer `, 쿠키 값, JWT(`eyJ`로 시작하는 세 덩어리)
- 키·토큰: `sk-`, `ghp_`, `glpat-`, `AKIA`, `api_key=`, 개인 키 블록
- 개인·고객 식별정보: 카드번호, 주민·사업자번호, 사번, 실명·연락처, 실제 데이터 행(건수·합계만 남긴다)

`sb lint`도 흔한 패턴을 잡지만 전부는 아니다. 의심되면 쓰지 않는다.

## 7. 점검

쓴 뒤 실제 파일을 다시 읽고 `sb lint "<절대 경로>"` — 이번 생성·변경으로 생긴 문제는 0건이 될 때까지 고친다. 기존 문제는 `SKILL.md` 7절 2번의 정책을 따른다. 보고에 중복 확인 결과(찾은 키, 같은 증상으로 걸린 노트, 함께 걸렸지만 증상·원인이 달라 제외한 노트)와 남긴 검증 범위·미확인 범위를 적는다.
